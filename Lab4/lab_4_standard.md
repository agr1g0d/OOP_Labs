# Лабораторная работа 4. Бэггинг моделей и адаптер признаков

Основной трек. Здесь объединены объяснения и условие.
Вариант со звёздочкой — самостоятельный альтернативный документ о random forest.
Выполняется один выбранный вариант. Новый базовый метод изучать не требуется:
используются kNN и NW из работ 2–3.

## Цель и исходные данные

Собрать ансамбль из независимо обучаемых моделей, реализовать адаптер выбора
признаков, управлять случайностью и распараллелить независимые вычисления.
Ансамбль снаружи используется как обычная модель.

Используются подготовленные данные предыдущих работ. Разбиение на обучение и
тест одинаково для всех сравниваемых моделей. Объекты ансамбля выбираются
только из обучающей части. Тестовые отклики не влияют на выборки или обучение.
Обе постановки реализуются; отсутствующую в своём датасете проверяйте на
маленьком синтетическом наборе.

## Концепция бэггинга

Несколько моделей обучаются на разных случайных версиях одной выборки.
Потом их ответы объединяются. Ошибки элементов ансамбля могут частично компенсироваться;
это особенно полезно, когда отдельная модель чувствительна к составу обучения.
Одинаковые модели на одинаковых данных дадут одинаковые ответы, и одно
усреднение ничего нового не добавит.

Классический bootstrap выбирает объекты с возвращением: один объект может
попасть в выборку несколько раз, другой — ни разу. Бэггинг использует такие
выборки для разных элементов ансамбля. Здесь дополнительно выбираются случайные
подмножества признаков. Комбинацию выборок объектов и признаков также называют
random patches. В этой работе используем название «бэггинг с выбором признаков».

Регрессоры усредняют числа, классификаторы — вероятности классов.

## Обязательные параметры и план обучения

| Параметр | Смысл |
|---|---|
| `n_estimators = B` | Число моделей в ансамбле, целое не меньше 1 |
| `sample_fraction = alpha` | Доля объектов на элемент ансамбля, `0 < alpha <= 1` |
| `feature_fraction = beta` | Доля признаков на элемент ансамбля, `0 < beta <= 1` |
| фабрика базовой модели | Создание нового необученного kNN или NW |
| `random_state` | Явный seed |
| `n_jobs` | Ограничение параллельных задач, не меньше 1 |

Доли конечны. Для `n` обучающих объектов и `d` признаков:

$$
m=\lceil\alpha n\rceil,\qquad q=\lceil\beta d\rceil.
$$

Для каждого элемента ансамбля:

1. Выбрать `m` индексов равновероятно из `[0,n)` **с возвращением**.
2. Выбрать `q` разных индексов признаков из `[0,d)` **без возвращения**.
3. Сохранить выбранные признаки в фиксированном порядке, например по возрастанию.
4. Создать новый экземпляр базовой модели и адаптер с этими признаками.
5. Сформировать выборку объектов и откликов с сохранением повторений.
6. Обучить элемент ансамбля через адаптер.

Повторения объектов нельзя удалять: они влияют на веса/голоса. При `alpha = 1`
получается `n` случайных извлечений, а не все исходные строки по одному разу.
Не нужно принудительно включать каждый класс или пересэмплировать «неудачную»
выборку: это изменило бы оговорённый bootstrap.

Набор признаков элемента ансамбля выбирается один раз при его обучении и затем
используется для всех запросов. В каждом следующем `fit` он генерируется заново
из того же seed по тому же правилу. Если после one-hot категории представлены
несколькими столбцами, здесь выбираются столбцы готовой матрицы, а не группы
исходных признаков. Групповой выбор не требуется.

Для kNN проверьте в `fit` ансамбля совместимость `k <= m`; не меняйте `k`
автоматически. Обязательны два режима: ансамбль kNN и ансамбль NW.
У каждого режима элементы ансамбля имеют одинаковые гиперпараметры, но разные
выборки и признаки. Смешивать типы моделей в одном ансамбле необязательно.

## Адаптер выбора признаков: интерфейсы и обязанности

Каждая модель в ансамбле получает собственный набор столбцов. Чтобы сам kNN
или NW ничего не знал об этом выборе, оберните его адаптером. Внешний код
передаёт полную матрицу, адаптер выбирает столбцы, вложенная модель получает
только нужные ей признаки.

Общий механизм здесь — проекция матрицы. Её реализует один класс:

```cpp
class FeatureSubset {
public:
    explicit FeatureSubset(std::vector<std::size_t> columns);
    Matrix project(const Matrix& X) const;

private:
    std::vector<std::size_t> columns_;
};
```

`project` проверяет номера столбцов и строит новую плотную матрицу в сохранённом
порядке. Набор непустой, без повторений. Произвольная группа столбцов может
не иметь постоянного шага, поэтому здесь допустима копия; не нужно превращать
`MatrixSlice` в универсальную произвольную индексацию.

Далее идут **два адаптера**, по одному на тип задачи. Оба используют готовый
`FeatureSubset`, поэтому код выбора и копирования столбцов пишется один раз:

```cpp
class FeatureSubsetRegressor final : public IRegressor {
public:
    FeatureSubsetRegressor(std::unique_ptr<IRegressor> model,
                           std::vector<std::size_t> columns);
    void fit(const Matrix& X, std::span<const double> y) override;
    std::vector<double> predict(const Matrix& X) const override;

private:
    std::unique_ptr<IRegressor> model_;
    FeatureSubset subset_;
    std::optional<std::size_t> input_features_;
};

class FeatureSubsetClassifier final : public IClassifier {
public:
    FeatureSubsetClassifier(std::unique_ptr<IClassifier> model,
                            std::vector<std::size_t> columns);
    void fit(const Matrix& X, std::span<const double> y) override;
    std::vector<double> predict(const Matrix& X) const override;
    Matrix predict_proba(const Matrix& X) const override;
    std::span<const double> classes() const override;

private:
    std::unique_ptr<IClassifier> model_;
    FeatureSubset subset_;
    std::optional<std::size_t> input_features_;
};
```

Общий класс `FeatureSubset` выполняет проекцию, а каждый адаптер проверяет состояние,
вызывает проекцию и делегирует операцию вложенной модели. У классификатора
дополнительно есть вероятности и список классов; регрессору они не нужны.
Никакой скрытой общей иерархии с распознаванием типов здесь нет.

`input_features_` сохраняется после успешного обучения: при предсказании
проверяется полное исходное число признаков, а не только выбранные индексы.
`classes()` просто делегируется вложенному классификатору.

Один универсальный класс `BootstrapAdapter` в этом варианте не требуется.
Bootstrap объектов подготавливается ансамблем, проекцию признаков делает
адаптер, а ответ нескольких моделей объединяет `BaggingRegressor` или
`BaggingClassifier`. Это три отдельные ответственности.

Для общего кода выборки можно использовать простой план:

```cpp
struct BootstrapPlan {
    std::vector<std::size_t> rows;    // повторения сохраняются
    std::vector<std::size_t> columns; // без повторений
};
```

Одна вспомогательная функция создаёт такие планы и для регрессии, и для
классификации. Отдельно можно выделить копирование строк с откликами.
Не дублируйте всю подготовку данных в двух ансамблях.

**`dynamic_cast` и `typeid` для распознавания конкретной модели запрещены.**
Работайте через `IRegressor`/`IClassifier`; адаптер не знает, находится внутри
kNN, NW или другой совместимый класс. Наследоваться от конкретного kNN/NW
ради выбора столбцов тоже нельзя.

Время жизни данных важно: матрица проекции, созданная локально в `fit`,
уничтожится после возврата из метода. Вложенная NW/kNN должна сохранять нужные
обучающие данные во владении, либо адаптер должен сам владеть этой матрицей.
Ссылка на уже уничтоженную локальную матрицу недопустима.

## Ансамбль: параметры и создание новых моделей

В Python можно передать класс и словарь аргументов. Здесь используем функцию,
которая уже знает, **как создать одну нужную модель с нужными параметрами**.
Такая функция называется фабрикой. Ансамбль вызывает её несколько раз;
на каждом вызове получается новый независимый необученный объект.

Не нужно передавать тип модели и все её параметры в шаблон ансамбля.
Параметры базового метода захватывает лямбда, параметры самого ансамбля
лежат в отдельной структуре:

```cpp
#include <cstdint>
#include <functional>
#include <memory>

struct BaggingParams {
    std::size_t n_estimators = 10;
    double sample_fraction = 0.5;
    double feature_fraction = 0.5;
    std::uint32_t random_state = 42;
    std::size_t n_jobs = 1;
};

using RegressorFactory =
    std::function<std::unique_ptr<IRegressor>()>;
using ClassifierFactory =
    std::function<std::unique_ptr<IClassifier>()>;

class BaggingRegressor final : public IRegressor {
public:
    BaggingRegressor(BaggingParams params, RegressorFactory factory);
    void fit(const Matrix& X, std::span<const double> y) override;
    std::vector<double> predict(const Matrix& X) const override;

private:
    BaggingParams params_;
    RegressorFactory factory_;
    std::vector<std::unique_ptr<IRegressor>> models_;
    std::optional<std::size_t> input_features_;
};

class BaggingClassifier final : public IClassifier {
public:
    BaggingClassifier(BaggingParams params, ClassifierFactory factory);
    void fit(const Matrix& X, std::span<const double> y) override;
    std::vector<double> predict(const Matrix& X) const override;
    Matrix predict_proba(const Matrix& X) const override;
    std::span<const double> classes() const override;

private:
    BaggingParams params_;
    ClassifierFactory factory_;
    std::vector<std::unique_ptr<IClassifier>> models_;
    std::vector<double> classes_;
    std::optional<std::size_t> input_features_;
};
```

Это каркас, а не готовая реализация. Если для вашей организации нужны планы,
seed или дополнительное обученное состояние, добавьте соответствующие поля.
Конструктор проверяет параметры ансамбля и непустую фабрику; `fit` проверяет
совместимость с данными и результат фабрики. Возврат `nullptr` — ошибка.

### Пример фабрики и передачи гиперпараметров

В примере предполагается конструктор NW вида
`NwRegressor(double bandwidth, std::unique_ptr<IDistance> distance)`.
Если у вашего класса другой порядок аргументов, изменится только лямбда.

```cpp
double bandwidth = 0.7;

RegressorFactory make_nw = [bandwidth]() -> std::unique_ptr<IRegressor> {
    return std::make_unique<NwRegressor>(
        bandwidth, std::make_unique<EuclideanDistance>()
    );
};

BaggingParams params;
params.n_estimators = 20;
params.sample_fraction = 0.3;
params.feature_fraction = 0.5;
params.random_state = 123;
params.n_jobs = 4;

BaggingRegressor ensemble(params, make_nw);
ensemble.fit(X_train, y_train);
auto predictions = ensemble.predict(X_test);
```

`[bandwidth]` сохраняет копию числа внутри лямбды. Фабрика может жить дольше
локальной переменной `bandwidth`; здесь нет ссылки на неё. При каждом вызове
создаётся новая NW и **новая метрика**. Для другого bandwidth создайте другую
лямбду; для kNN замените тело на создание kNN. Математика ансамбля не меняется.
Классификатор создаётся точно так же через `ClassifierFactory` и
`BaggingClassifier`.

Для проверки самой идеи:

```cpp
auto first = make_nw();
auto second = make_nw();
// first и second владеют разными объектами.
```

Передача владения в адаптер выглядит так; выбранные индексы здесь показаны
вручную, в ансамбле они приходят из `BootstrapPlan`:

```cpp
auto base = make_nw();
auto wrapped = std::make_unique<FeatureSubsetRegressor>(
    std::move(base), std::vector<std::size_t>{0, 2}
);
// base теперь пуст; моделью владеет wrapped.
```

Внутри ансамбля такой адаптер сохраняется в `models_` через указатель на
`IRegressor`. Аналогичный адаптер классификатора сохраняется через
`IClassifier`. Внешний код по-прежнему передаёт полную матрицу.

Нельзя создать одну метрику в `unique_ptr`, а затем многократно перемещать
её в новые модели: после первого `std::move` указатель уже пуст.
Лямбда, захватывающая `unique_ptr` по значению через перемещение, также
не подходит для обычного копируемого `std::function` в C++20.
Простой рекомендуемый вариант — каждый раз создавать новую метрику внутри
лямбды, как выше. Копирование обученной модели и `clone` не требуются.
Все фабрики и адаптеры можно создавать последовательно до запуска рабочих
потоков; пользовательская фабрика не обязана быть потокобезопасной.

## Объединение ответов

Для регрессии усредняются предсказания моделей:

$$
\hat y(x)=\frac1B\sum_{b=1}^{B}\hat y_b(x).
$$

Для классификации постройте общий список классов по исходному `y_train`.
Bootstrap-выборка отдельной модели может не содержать части классов;
согласуйте её столбцы по `classes()`, отсутствующему классу соответствует 0.

$$
\hat p_c(x)=\frac1B\sum_{b=1}^{B}\hat p_{b,c}(x),\qquad
\hat c(x)=\operatorname*{argmax}_c\hat p_c(x).
$$

Номера классов не усредняются. `predict` выбирает максимальную среднюю
вероятность, при ничьей — меньшую метку. Голосование по уже выбранным меткам
не заменяет это правило.

## Почему подвыборки могут ускорить NW

Для используемых расстояний один запрос NW по `n` объектам и `d` признакам
стоит `O(nd)`. Пакет из `r` запросов стоит `O(rnd)`; если `r` порядка `n`,
получается квадратичная зависимость по числу объектов. Обучение NW в основном
сохраняет данные и не вычисляет все попарные расстояния.

Ансамбль с `B` элементами ансамбля по `m` объектам и `q` признакам имеет стоимость
предсказания порядка `O(B*r*m*q)` без учёта проекций и суммирования. По сравнению
с полной NW объём работы может уменьшиться, если `B*m*q < n*d`, а может
увеличиться. Одно лишь уменьшение выборки каждой модели не гарантирует
ускорения всего ансамбля. Дополнительно возможен выигрыш от параллельности.
Копирование матриц проекции и память элементов ансамбля тоже имеют стоимость.

В плотной области похожие объекты иногда частично дублируют информацию,
поэтому подвыборка может сохранить приемлемое качество. Это мотивация,
а не гарантия: редкие классы, границы и малый bandwidth могут пострадать.
Нельзя утверждать заранее, что прореживание почти ничего не теряет.

## Жизненный цикл, воспроизводимость и параллельные вычисления

Конструктор сохраняет гиперпараметры и зависимости и проверяет ограничения,
не требующие данных. `fit` проверяет выборку и строит весь ансамбль заново;
модели не накапливаются при повторных вызовах. Для другой конфигурации
создаётся новый объект. `predict` и `predict_proba` обученное состояние
не меняют. При ошибке обучения частично построенный ансамбль не должен
считаться обученным: сохраните прежнее состояние или явно сбросьте обучение,
опишите и проверьте выбранное правило.

### Разные seed для разных элементов ансамбля

**Разные элементы ансамбля должны обучаться с разными seed. Нельзя всем
моделям передать один и тот же `random_state` и ожидать разного bootstrap.**

Для обычного трека это разные seed генерации выборок объектов и признаков;
для леса — также генерации признаков в узлах дерева. Сначала по общему
`random_state` и номерам элементов подготовьте их разные seed в фиксированном
порядке. Можно сформировать список уникальных seed, проверяя повторения.
Каждый элемент получает собственный `std::mt19937`; общий изменяемый RNG
между потоками не используется.

Одинаковые вход, параметры и общий seed должны воспроизводить планы и ответы
в одном окружении независимо от числа потоков. Повторный `fit` начинает
генерацию заново, а не продолжает прежнее состояние RNG. Другой seed может,
но не обязан менять каждый ответ на простых данных. Побитового совпадения
между Python и C++ или разными стандартными библиотеками не требуется.

### Распараллеливание только через `std::jthread`

Реализуйте последовательное и параллельное обучение элементов ансамбля,
а также параллельное получение их предсказаний. Для создания потоков в этой
работе используется **только `std::jthread` из C++20**.
`n_jobs >= 1` ограничивает число рабочих потоков. При `n_jobs == 1`
используйте последовательный путь, при числе моделей меньше `n_jobs`
не создавайте лишние потоки.

Достаточно назначить каждому рабочему потоку несколько номеров моделей,
например `worker_id`, `worker_id + p`, `worker_id + 2*p`, где `p` — число
рабочих потоков. Универсальная очередь задач и собственный планировщик
не требуются. Один поток на каждую модель без ограничения `n_jobs` не подходит.

`std::jthread` при уничтожении ожидает завершения своего потока. Но результат
нельзя суммировать раньше этого ожидания: ограничьте группу потоков отдельным
блоком или явно вызовите `join()` у каждого перед чтением результатов.

Правила:

- исходная матрица и отклики доступны рабочим задачам только для чтения;
- элемент ансамбля и его генератор изменяет только один поток;
- контейнеры моделей, результатов и ошибок подготовлены до запуска потоков;
  совместного `push_back` нет;
- каждая задача пишет в своё место результата, а финальное среднее считается
  в порядке номеров моделей, а не порядка завершения;
- все захваченные по ссылке данные живут до завершения потоков;
- вложенная модель не использует общий изменяемый рабочий буфер без защиты;
- исключение перехватывается **внутри** рабочей функции и сохраняется через
  `std::current_exception()` в заранее подготовленную ячейку
  `std::exception_ptr` этой задачи; после завершения всех потоков ошибка
  передаётся вызывающему коду через `std::rethrow_exception()`.

Сам по себе `std::jthread` не передаёт исключения между потоками и не устраняет
гонки данных. Распараллеливать одновременно элементы ансамбля, отдельные
объекты и внутренние циклы расстояний не требуется: достаточно верхнего уровня.

**Написание кода с `std::jthread`, обработку ошибок потоков и его отладку
можно поручить ИИ-агенту. Итоговый код студент обязан понимать и уметь объяснить.**
До этого самостоятельно определите независимые задачи, владельцев данных,
правило seed и порядок агрегации; сначала проверьте последовательный вариант.

### Измерение времени

Измеряйте Release-сборку без санитайзеров на одинаковых данных и параметрах.
Подготовку данных, `fit` и пакетный `predict` измеряйте отдельно; загрузку CSV
не включайте в предсказание. Сделайте несколько повторов и сообщите медиану,
размеры данных, параметры, число потоков, компилятор и компьютер.

Сравните `n_jobs=1` и хотя бы одно большее значение. Ускорение — `T_1/T_p`.
Линейного выигрыша не требуется: на небольшой задаче затраты запуска потоков
могут перевесить пользу. Отсутствие ускорения объясните, не скрывайте его.

## Программа, проверки и демонстрация

Приложение обучает одиночную модель на полном обучающем наборе и ансамбль
того же типа. Выводит параметры, размеры `m`, `q`, несколько предсказаний
рядом с ответами и времена. Для классификации показывает вероятности и
порядок классов. Сравнение по точности не обязано давать преимущество ансамбля.

Для небольшого эксперимента достаточно посчитать в приложении MAE для своей
регрессионной задачи или accuracy для классификации. Это несколько строк
диагностики, не отдельная иерархия метрик и не подбор параметров. Используйте
одну заранее заданную конфигурацию; тестовую часть не подбирайте под желаемый
результат. Полный эксперимент с параметрами будет в работе 5.

Обязательные тесты:

- адаптер совпадает с ручной проекцией при `fit` и `predict`, сохраняет порядок
  столбцов, проверяет индексы и не оставляет висячих ссылок;
- фабрика вызывается `B` раз, каждый экземпляр независим;
- контролируемая выборка сохраняет bootstrap-повторения, а признаки уникальны;
- при всех выбранных признаках адаптер эквивалентен исходной модели;
- известные ответы тестовых элементов ансамбля дают правильное среднее;
- вероятности согласованы по меткам, даже если у элемента ансамбля нет одного класса;
- случай `B = 1` равен именно своему единственному bootstrap-элементу ансамбля,
  а не обязательно модели, обученной на полном исходном наборе;
- одинаковый seed воспроизводит планы и ответы, повторный `fit` не накапливает
  элементы ансамбля, оба layout дают одинаковые логические результаты;
- последовательная и параллельная версии дают одинаковые планы и ответы
  с численным допуском;
- ошибка одной задачи доходит до вызывающего кода после корректного завершения
  остальных потоков; проверяются `n_jobs > B` и ошибочные параметры;
- граничные случаи: один объект, один признак, один класс, маленькие доли,
  несовместимый `k`, пустой пакет запросов.

## Самостоятельная часть и работа с агентом

Самостоятельно проектируются композиция, владение, фабрика/создание элементов ансамбля,
выборки объектов и признаков, RNG и распределение seed, агрегация и согласование
классов. Изменения алгоритма базовой модели также пишутся самостоятельно.
Сначала получите и проверьте последовательную реализацию.

Главная задача для агента — написать с использованием `std::jthread`
ограниченное распараллеливание уже
определённых независимых задач, помочь с диагностикой и проверками.
Студент заранее задаёт границы задач, владельцев данных, правило seed и порядок
суммирования. Агент не выбирает вместо него схему ансамбля.
Документацию, тестовую инфраструктуру и освоенные ранее настройки сборки
тоже можно делать с агентом. Предметные ожидаемые ответы и свойства тестов
проверяет студент. Эти правила действуют и для трека со звёздочкой:
алгоритм леса и проектные решения самостоятельные, явно разрешённая
инфраструктура — с агентом.

Разрешено просить объяснить средство языка; нельзя поручать готовую реализацию
изучаемого алгоритма. Граница задаётся темой работы, а не длиной функции.
Любой принятый код нужно уметь объяснить и изменить без агента.
В `docs/agent_log/lab_4.md` фиксируются значимые запросы, что принято/изменено/
отклонено, способы проверки и обнаруженные проблемы. Обновите `AGENTS.md`.

## Общие требования и сдача

- C++20, CMake, библиотека ядра отдельно от приложения, тесты в CTest,
  сборка без предупреждений при `-Wall -Wextra`.
- В Debug работают ASan/UBSan. Если среда поддерживает ThreadSanitizer,
  его можно запустить отдельно; одновременно с ASan его не подключают.
- Алгоритмы и метрики машинного обучения из сторонних библиотек не используются.
- Модели сохраняют интерфейсы `IModel`, `IRegressor`, `IClassifier` из работы 3.
  Для классификации `classes()` определяет порядок столбцов `predict_proba`.
- Ядро сообщает об ошибках исключениями и не печатает. Приложение перехватывает
  ошибку, показывает сообщение и возвращает ненулевой код.
- Проверяются пустое обучение, отсутствие признаков, несовпадение размеров,
  нечисловые/бесконечные входы и несовместимые параметры. `predict` до обучения
  запрещён. Ноль тестовых объектов возвращает пустой результат правильной формы.
- После `fit` нет ссылок на уничтоженные локальные матрицы и представления.
  Выбор layout не меняет логические ответы.
- Тесты не зависят от случайного удачного попадания: для точных ожидаемых
  ответов подавайте контролируемые элементы ансамбля/планы, а свойства RNG проверяйте
  отдельно. Тестовые вспомогательные типы не должны усложнять рабочий API.

Сдаются продолжение репозитория, актуальные README и документация интерфейсов,
`AGENTS.md`, журнал `docs/agent_log/lab_4.md`, тесты и результаты измерений.
В README опишите владение и создание элементов ансамбля, random_state, порядок
суммирования, обработку ошибок потоков и стоимость вычислений.

Зачёт требует работоспособности, самостоятельной реализации предметной части,
прохождения тестов и понимания кода. Улучшение точности или ускорение на
каждом датасете не является условием зачёта. Подбор параметров и полноценный
анализ качества остаются содержанием работы 5; её звёздочка — permutation
feature importance, реализовывать её здесь не нужно.
